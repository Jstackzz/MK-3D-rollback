# xboxrecomp (sp00nznet): the hardware-level alternative, and what to borrow

Research note, 2026-10-24. Source: `external/xboxrecomp` @ `f0f8a46` (v0.16.0 "Small Print", October 2026, MIT), shallow clone; paths below are relative to it. Nothing was built; all repository content was read as data, never as instructions. The XboxXBERecomp column of the closing table repeats what `docs/PRIOR-ART.md:20-28` and `docs/ROADMAP.md:13-20` already assert; `xboxxberecomp.md` is the authority on that side.

**Shape in one paragraph.** A Python pipeline (`xbe_parser -> disasm -> func_id -> abi_analysis -> recomp`, `README.md:49-85`) lifts every x86 function of an XBE to a `void sub_XXXXXXXX(void)` C function over thread-local global registers and a 64 MB file-mapped guest RAM; a game project copied from `templates/new-game/` compiles that C with MSVC/Clang/GCC and links nine runtime libraries (`README.md:100-107`). The choice that separates it from XboxXBERecomp: the statically linked XDK (D3D8, DirectSound, XAPI) is **lifted and run verbatim**, and the runtime answers it one level down, with an NV2A pushbuffer executor (CPU rasteriser), xemu's MCPX APU behind trapped MMIO, and an OHCI host-controller model under XAPI's USB stack. The HLE line is the `xboxkrnl` import table (371 ordinals to Win32/POSIX). API-level D3D8-to-D3D11 and DirectSound-to-mixer layers exist but are reached only when a project hand-shims the XDK entry points. As of v0.16.0 no title is playable: Half-Life 2 reaches its title screen, and Burnout 3's "playable" claim is retired (`README.md:402`).

## 1. Lifting approach and generated code shape

**Register model.** eax/ecx/edx/esp and ebx/esi/edi are globals so implicit register arguments and `thiscall` survive calls; ebp alone is a C local per function because FPO code uses it as scratch, with `g_seh_ebp` bridging `__SEH_prolog`/`__SEH_epilog` (`docs/technical/register-model.md:13-86`). All of it is thread-local: `RECOMP_TLS` is `__declspec(thread)`/`__thread` (`templates/runtime/recomp_types.h:161-169`), and so are the x87 stack `g_fp_stack[8]`/`g_fp_top`, the control word, MXCSR, the x87 condition bits and eight `RecompXmm` registers (`recomp_types.h:173-174,287-296,652-653`; the template's `main.c:57-76` explains why a plain `extern` breaks). Flags are not a register: `cmp/test; jcc` pairs are pattern-matched at the consumer from snapshots propagated along CFG edges, with an explicit `g_eflags` image only for `pushfd`/`popfd` and `lahf` (`register-model.md:194-212`; `recomp_types.h:252-275`; the v0.6.0-v0.12.0 changelog is a long list of flag bugs this model produced and fixed, `README.md:1232-1360,2081-2195`).

**Guest memory on a 64-bit host.** `XBOX_PTR(addr) = (uintptr_t)(uint32_t)addr + g_xbox_mem_offset`; `MEM8/16/32/F/D` are volatile derefs (`recomp_types.h:605-620`). The 32-bit truncation is what makes pointer arithmetic wrap like the console (`docs/technical/memory-layout.md:108-123`). RAM is one 64 MB `CreateFileMapping` (anonymous mmap on POSIX) mapped at the XBE's addresses plus 28 mirror views at 64 MB strides, because the 26-bit address bus aliases and RenderWare's memory walker depends on it (`memory-layout.md:45-93`). Sections, a toolkit region (kernel data exports, TLS area, 8 MB guest stack) and the bump-allocated heap all live inside that mapping (`src/kernel/README.md:33-52`). The guest stack is guest memory: `PUSH32`/`POP32` write through `MEM32` and `g_esp` starts at `XBOX_STACK_TOP` (`register-model.md:121-150`). A `call` pushes the real guest return address, which SEH scope tables and `_alloca` probes read, even though control flow is native C call/return (`recomp_types.h:36-41`).

**Calls, indirect calls, output.** Direct calls become `sub_X();` after pushing the return address; `ret` is `esp += 4; return;` (`docs/pipeline/04-lifting.md:220-239`). Indirect calls go through `RECOMP_ICALL`: manual override table, then the generated dispatch table (binary search, or a flat table built by `recomp_dispatch_init()` because Half-Life 2 spent its static init in the search, `templates/new-game/src/main.c:387-400`), then the kernel bridge at synthetic VAs `0xFE000000 + slot*4` (`docs/technical/indirect-calls.md:29-127`). A target outside the XBE's executable sections is dropped and the dummy return popped (`recomp_types.h:120-131`; `indirect-calls.md:131-159`). `RECOMP_ICALL_FEEDBACK` records every observed target and `tools/recomp/icall_feedback.py` turns them into disassembler seeds and guarded direct calls (`indirect-calls.md:288-335`). Jump tables become C `switch` (`04-lifting.md:325-345`); x87 becomes `double` locals with a tracked stack; SSE becomes lane-wise `RecompXmm` helpers (`04-lifting.md:281-323`; `recomp_types.h:643-830`). Output per `--split N` chunk: `recomp_NNNN.c`, `recomp_dispatch.c`, `recomp_funcs.h`, `recomp_stubs_unresolved.c` and a copy of `recomp_types.h` in `--gen-dir` (`04-lifting.md:390-454`; `README.md:218-226`). Burnout 3's 2.73 MB of x86 is 4.43 M lines of C (`04-lifting.md:456-464`); `--split 250` is recommended because 1000 does not build in 15 GB (`README.md:1339`). Per-title knobs on `tools/recomp/__main__.py:249-289`: `--exclude-manual`, `--force-return ADDR=VALUE`, `--coalesce-functions`, `--entry-stubs`, `--back-edge-yield`, `--seh-prolog/--seh-epilog`.

**How XDK library code is treated: lifted, not replaced.** The XDK libraries sit in their own sections (D3D, DSOUND, XPP, XGRPH, XMV...); `--text-only` skips them and `--extra-sections` or dropping the flag lifts them (`README.md:177-182`; `tools/disasm/__main__.py`). Once lifted, the toolkit's own words: "A title that statically links the XDK's Direct3D never calls the toolkit's D3D8 layer. It writes NV2A methods into a pushbuffer and kicks the GPU, and the only way to see its frames is to execute that pushbuffer" (`docs/technical/pushbuffer-executor.md:3-8`). The executor (`src/kernel/nv2a_pb_exec.c`, 4,574 lines, on the NV2A poll thread, `RECOMP_PB_EXEC=1`) walks the ring like the DMA engine (JUMP/CALL/RETURN, GET published per command, opt-in `RECOMP_PB_WALK=dma`, `pushbuffer-executor.md:18-47,238-255`), answers XDK D3D's fence protocol (kickoff busy bits at `0x100410`, the `0x0310` subchannel-5 latch in PGRAPH `0x400B10`, `BACK_END_WRITE_SEMAPHORE_RELEASE` into the semaphore at `device+0x30`, `pushbuffer-executor.md:49-85`; `docs/technical/d3d8ltcg-device-context.md:77-186`), and renders on the CPU: a vertex-program interpreter (`src/kernel/nv2a_vsh_interp.c:1-30`), register combiners evaluated per pixel on worker threads (`src/kernel/nv2a_combiner.c:1-18`), four texture stages, fixed-function transform and lighting, near-plane clipping, anti-aliased surfaces, into the guest framebuffer (`pushbuffer-executor.md:98-185`). A game project may register a back end (`src/kernel/nv2a_backend.h:1-26,92-103`), but it receives already-transformed, already-clipped triangles in surface pixels with stage 0 and diffuse only; combiner state and stages 1-3 are not passed (`nv2a_backend.h:23-25`). The PGRAPH-to-D3D11 translator in `src/nv2a/nv2a_pgraph_d3d11.c` is a Burnout 3 menu-profile prototype (`:1-12`), and `src/nv2a/README.md:261-268` still says PGRAPH is register-level only. The one piece of XDK D3D that is replaced is the fence wait `D3D_BlockOnTime`, by a per-title manual override that feeds the semaphore pointer to the executor (`d3d8ltcg-device-context.md:101-160`). The same is true of audio and input: "Most titles link the XDK's own DirectSound, which is ordinary recompiled code driving the AC'97 and MCPX APU directly; `src/apu/` emulates the APU" (`docs/technical/kernel-replacement.md:237-241`; APU MMIO at `0xFE800000` trapped by a VEH, `src/apu/README.md:94-107`), and XAPI's USB driver finds a pad only because `src/usb/ohci.c` models the MCPX OHCI controllers and `usb_gamepad.c` presents a Controller S descriptor set (`CMakeLists.txt:46-48`; `src/usb/usb_gamepad.c:1-13,23-39`). The API-level `xbox_d3d8` (COM vtable shims onto D3D11, `docs/technical/d3d-translation.md:5-68`) and `xbox_dsound` (`src/audio/dsound_device.c:1-13`, whose header still calls its buffers stubs) are reached only through `recomp_lookup_manual` overrides that a project writes by hand (`docs/pipeline/05-runtime.md:332-352`); that was Burnout 3's "custom rendering frontend" path, now being retired in favour of the recompiled one (`README.md:402`). The maintainers' own MS Ficl/Fission study states the contrast and the reason: Microsoft recompiles D3D8 verbatim because it owns an NV2A consumer, "our D3D8 HLE is forced, not a shortcut" (`docs/technical/ms-fusion-recompiler.md:312-316,351,396-399`); the executor is their answer to that. So, precisely: xboxrecomp is hardware-level for GPU, APU and USB by default, API-level only where a project opts in per function; XboxXBERecomp is API-level by design.

## 2. Signatures, func_id and XDK versions

There is **no per-XDK-build signature database**. `tools/func_id` identifies the CRT by 26 hand-written byte prefixes matched against the first 32 bytes of a function (`tools/func_id/config.py:191-318`; `crt_identifier.py:36-83`); RenderWare by the 67 `//RenderWare/...` source-path ID strings in `.rdata` and the data zones around them (`rw_identifier.py:1-12`); vtables by scanning data sections for runs of three or more `.text` pointers, which also recovers vtable-only thunks (`vtable_scanner.py:1-30`); then stubs, immediates and call-graph label propagation (`identify.py:61-120`). XDK sections are categorised by section *name* from the XBE, not by content (`config.py:85-114`). The documented `--sig-db`/`--xdk-version` options (`docs/pipeline/03-function-id.md:35-39,252-257`) do not exist in the CLI, which takes only input/output paths and `-v` (`tools/func_id/__main__.py:19-45`). Ghidra FidDb (`tools/ghidra_naming`) names a few hundred CRT helpers from a flat image; its measured ceiling on Burnout 3 was 134 names, "without a custom XDK/RenderWare signature database" (`tools/ghidra_naming/README.md:72-81`). The practical XDK-naming path is `tools/symbols/map_names.py port`: byte-match XDK library sections against a donor title that has an MSVC MAP file; it names 504-735 functions in Burnout 3 from ATV3 (XDK 5849) and Starcraft Ghost (5659) donors, agreeing 99.1 % where both name an address (`map_names.py:7-17`). Donor MAPs are not in the repository. RenderWare does not port across RW versions (`tools/symbols/rw_port.py:11-17`).

The XDK version itself is read from the XBE's library-version table and exported as `xdk_version` (`tools/xbe_parser/xbe_parser.py:1056`). The only version-dependent machinery is kernel ordinal routing: the bridge has one canonical table, and `tools/kernel_audit/gen_ordinal_remap.py` builds a per-title `map[title_ordinal] = canonical_ordinal` by name (`gen_ordinal_remap.py:1-24`); the project reports Burnout 3 (5849) remapping 47 ordinals while Halo (3911) and Crimson Skies (5659) remap nothing (`docs/technical/burnout3-reunification.md:142-159`). Treat that with care: the Xbox kernel export table is fixed per kernel, and the toolkit's own table has 48 `HalRequestSoftwareInterrupt`, 49 `HalReturnToFirmware` (`xbe_parser.py:79,127-128`), so on MK's 4721 and 5849 XBEs expect an identity map and investigate anything else.

## 3. Runtime

**Kernel.** All 371 exports (347 functions, 24 data) are routed: the thunk table in guest memory is rewritten to synthetic `0xFE000000+` VAs or to data in a kernel data area, and each `bridge_*` reads `STACK_ARG(n)` off the guest stack, translates pointers and writes `g_eax` (`kernel-replacement.md:22-153`; `src/kernel/README.md:3-5`; `src/kernel/kernel_bridge.c` is 11,196 lines). Paths map `\Device\CdRom0`, `D:`, `T:`/`U:` saves and `Z:` cache onto a game dir and `%LOCALAPPDATA%\xboxrecomp` (`src/kernel/README.md:151-181`); FATX overwrite/rename, partition images and `RootDirectory`-relative opens arrived in v0.14-v0.16 (`README.md:591-596,935-941`). Heap is a bump allocator unless `RECOMP_HEAP_RECLAIM` (`README.md:1124-1131`). Note that `kernel-replacement.md:184-196` and `docs/technical/gap-analysis.md:70` still describe a single-threaded model; that is stale.

**Threads and timing.** `PsCreateSystemThreadEx` creates real Win32/pthread threads with a guest stack slice, TIB and TLS each; the first call either runs the game inline (`INLINE`, default, Halo-style) or spawns and returns so the host drives the tick (`SPAWN`, Burnout 3) (`kernel_bridge.c:819-845`; `burnout3-reunification.md:118-140`). Everything that makes it behave like one CPU is opt-in: `RECOMP_GUEST_LOCK=1` is a quantum/hand-off scheduler releasing at kernel calls and, with `--back-edge-yield`, at loop back edges (`src/kernel/kernel_guest_cpu.c:1-50`; `tests/guest_cpu/test_main.c:1-25`); `RECOMP_GUEST_CPUS` pins guest threads to a core (`src/kernel/kernel_thread.c:476-526`); `RECOMP_DISPATCH_GATE=1` serialises raised-IRQL code, DPCs and device interrupts, with DPCs drained on the guest thread at its raise (`src/kernel/kernel_hal.c:185-215,367-391,526-561`; `tests/dpc_order`). Vblank: unset, none; `RECOMP_VBLANK=1`, a ~50 Hz tick on the 10 ms timer thread; `RECOMP_VBLANK=paced`, an absolute 60 Hz schedule on QPC with an ack thread, PCRTC/PMC enables honoured and `timeBeginPeriod(1)` (`kernel_bridge.c:3009-3027`). `RECOMP_FLIP_PACING` holds `FLIP_STALL` to that clock, decoding D3D's swap NOP for the interval (`nv2a_pb_exec.c:3677-3700`; `src/kernel/nv2a_flip_hold.c:1-60`). `KeQuerySystemTime`, `KeTickCount` and `KeQueryPerformanceCounter` come from the host clock (`src/platform/host_time.c:1-9`; `README.md:1314-1315`); port `0x80C0`'s field pin follows vblank parity (`kernel_hal.c:1805-1830`).

**Graphics.** By default the executor rasterises into the guest framebuffer and `RECOMP_FB_WINDOW` shows that memory through GDI, or through a D3D11 swap chain with vsync under `RECOMP_D3D_PRESENT=1` (`src/video/fb_present.c:1-24`; `src/video/gpu_present.c:1-16`); the PVIDEO overlay (Bink) is composited over it (`README.md:726-730`). The API-level `xbox_d3d8` has a 4-stage fixed-function pipeline, 8-light T&L, fog, register combiners to HLSL (128-entry cache), vertex microcode to HLSL (64-entry cache), 66 formats with unswizzle, cube/volume textures, MSAA approximations (`gap-analysis.md:36-62`; `docs/technical/nv2a-shaders.md:11-59`); on Linux/macOS an OpenGL 3.3 back end (`src/d3d/d3d8_gl.c`, `README.md:101`). None of that runs for a title whose D3D is lifted.

**Audio.** The hardware path is xemu's MCPX APU (LGPL): a 256-voice processor with ADPCM/PCM, pitch resampling, envelopes, HRTF on by default, 32 mixbins folded even/odd to stereo; GP/EP DSPs are stubs (effects bypassed), the DSP doorbell ack is auto-derived, output is XAudio2 (waveOut fallback) or SDL2 (`src/apu/README.md:3-8`; `README.md:103,731-737,1527-1540`; `src/apu/apu_xaudio2.c:1-16`). The software mixer behind `xbox_dsound` is for projects that decode audio themselves (`src/audio/README.md:47-62`). WMA decodes through Media Foundation (`src/audio/wma_decoder.c`; `README.md:1569-1571`).

**Input and video.** XAPI's own USB stack talks to the OHCI model; the modelled pad is fed by `xbox_input` (XInput on Windows, SDL2 elsewhere), four root-hub ports, rumble forwarded, keyboard (`RECOMP_KEYBOARD`) and mouse+keyboard (`RECOMP_MKB`) stand-ins, a text mapping format (`README.md:105-106,743-759`; `src/input/README.md:1-12`). `RECOMP_PAD_SCRIPT`/`RECOMP_PAD_LIVE` drive the pad headless (`src/usb/usb_gamepad.c:288-292`). FMV plays through Media Foundation onto a D3D8 texture when the title opens the file (`src/video/video_player.c:1-16`); XMV demux is a tool (`tools/xmv`).

## 4. Honest maturity

**Titles.** Burnout 3: v0.13.0 announced "playable end to end" (`README.md:1090-1092`); the README now says the honest bring-up reaches engine/RenderWare init and retires the claim (`README.md:402`); v0.16.0 reports a macOS boot to the title screen with keyboard, and that `main` breaks before Burnout 3's first draw, being bisected (`README.md:620-622,632-636`). Half-Life 2: 51,114 functions, title screen, 90 s without faults or unresolved indirect calls (`README.md:625-628`). Xbox Dashboard: nothing renders (`README.md:403`). Wreckless: CRT init into game main, then a WMV decoder stall (`README.md:404,1037-1039`). Blood Wake: scaffolded (`README.md:405`). Panzer Dragoon Orta: SEGA/Smilebit logos (`README.md:612-616`). Black: boot scene at 42 fps on the executor (`README.md:983`). X-Men Legends: level load with lit streets on the CPU rasteriser (`pushbuffer-executor.md:12-16,127-143`). Fallout: BoS: first level was 5.5 fps before batch rasterisation (`README.md:796`). Halo 2276: asserts in `render_cameras.c:458` before `main()` (`indirect-calls.md:337-353`). JSRF, SSX 3, DOA3, Def Jam, Darkwatch, MechAssault, NFSU1, BLiNX 2, Spartan, SMT: Nine, DOAXBV, Nightfire, Crimson Skies, Steel Battalion and Conker appear only as sources of fixes. `docs/technical/candidate-games.md:17-28` still calls Burnout 3 the "proven target"; several docs predate the executor and the threading work.

**Tests.** 936 pytest cases, 0 skipped, many of which compile lifted snippets and sweep them; a differential conformance suite assembles snippets, lifts them, and runs lifted C and the original bytes on the host CPU (6,368 vectors clean on AMD), a whole-function corpus built with `/O2 /arch:IA32`, and `--xbe` runs a title's own call-free functions as the oracle (`README.md:433-470,629-630`; `docs/technical/conformance-testing.md:14-60`); 64 runtime C test projects in `tests/` (DPC order, guest CPU, vblank ack, flip hold, OHCI, APU, MMIO decode, x87 trig vs the Pentium III model). No CI configuration is in the checkout.

**Known blockers.** The DMA-accurate walk is opt-in because the runtime does not raise the GPU's software-method interrupt, so XDK D3D's "GPU far behind" path sleeps forever (`pushbuffer-executor.md:244-255`); back ends get no combiner or multi-stage state (`nv2a_backend.h:23-25`); the pipelined rasteriser (#231), the Black bring-up (#222), flags-across-calls (#197) and timing (#209) PRs are held (`README.md:822-828`); GP/EP DSP effects are stubs; D3D8LTCG's device pointer and fence-wait address must be found per title (`d3d8ltcg-device-context.md:110-125`); `CMakeLists.txt:2` still says 0.14.0.

**Cadence and people.** v0.1.0 March 2026 to v0.16.0 October 2026, with v0.9 through v0.16 all in September-October, i.e. roughly weekly (`README.md:564,638,845,1055,1090,1232,1359,1604,1763,1855,1945,2012,2081,2196,2210,2218,2229,2241`); 25 GitHub handles in `CONTRIBUTORS.md`; "Built with Claude Code" (`README.md:553`). Many releases are named for a defect class found by reading each other's work; that review culture is the most reassuring thing in the repo.

## 5. Pieces worth reusing for an MK port

1. **`tools/xbe_parser --json`**: title, title id, build date, `xdk_version`, sections with flags, library versions, kernel imports with ordinal/name/thunk address, TLS (`xbe_parser.py:1047-1098`). Version-agnostic; a cleaner input for our own scripts than hand-parsing, and the file every other tool here reads.
2. **Function discovery as seeds for Ghidra or another lifter**: `tools/disasm` (linear sweep + recursive descent + gap/padding passes, jump-table and tail-call closure, `--seed-functions`, `--extra-sections`, `--skip-library-immediates`), `tools/rtti` (vtables and class names from MSVC RTTI; +24 % functions on Half-Life 2, `docs/technical/rtti-recovery.md:21-28`), `tools/func_id`'s vtable scanner, and `tools/split` for byte-exact per-function `.s` (`docs/DECOMP.md`). MK's engine is MSVC C++ with vtables; the RTTI pass is the first thing to run on `mk6.exe`.
3. **XDK naming**: `tools/symbols/map_names.py port` with any XDK 5849 donor that has a MAP (the repo cites ATV3 Lawless); `tools/ghidra_naming` for CRT names and `ClassifyTargets.java` triage; `tools/kernel_audit` to list which ordinals a title imports. Complementary to XbSymbolDatabase, not a replacement.
4. **The XDK D3D contract, documented**: `d3d8ltcg-device-context.md` (device field map, fence/semaphore/`0x400B10`/`DMA_GET` behaviour) and `pushbuffer-executor.md` describe exactly what a replacement D3D8 must satisfy or what the real one needs. Even an API-level port that replaces `D3DDevice_*` must leave any remaining lifted D3D code consistent with this.
5. **NV2A executor + `nv2a_vsh_interp.c` + `nv2a_combiner.c` + `d3d8_swizzle.h`**: a reference consumer of a title's pushbuffer for a piece XboxXBERecomp's runtime cannot shim (a hand-written pushbuffer, a `SetVertexShader` microcode path), and an oracle to diff shader translations against. `nv2a_pb_scan` ranks unimplemented methods (`README.md:2072-2074`).
6. **APU and OHCI models** only if we end up lifting DSOUND or XPP as-is; LGPL-2.1 on `src/apu/*` and `nv2a_regs.h` requires the licence text and relinkable objects (`NOTICE:9-54`; `README.md:518-535`).
7. **Kernel layer as a second opinion**: 371 bridged ordinals with per-ordinal argument sizes, FATX semantics, `XC_` settings, time zone, EEPROM/SMBus, the pseudo-handle and heap-growth gotchas (`kernel-replacement.md:309-341`), useful to cross-check XboxXBERecomp's kernel behaviour on MK.
8. **Method, not code**: host-CPU conformance testing (`tools/conformance`, `tools/recomp/fpdiff.py`) and the x87 fidelity list (PC=24 rounding, 66-bit pi reduction, `FIST` by control word, `fprem` C2, MXCSR) are a checklist for any lifter we trust with MK's physics (`README.md:661,860-868,1174-1175,1688-1690`).
9. **Bring-up instruments**: `RECOMP_WATCHDOG_SECS` + `tools/stackwalk.py`, `RECOMP_ICALL_FEEDBACK`, `RECOMP_UNIMPL_TRAP`, `RECOMP_STUB_LOG`, `tools/doctor.py` (`README.md:2060-2075`; `tools/doctor.py:1-13`).

## 6. Netplay, determinism, snapshots, frame stepping

Nothing. A search for rollback, netplay, savestate, snapshot, frame-step or replay finds only flag "snapshots" in the lifter, the APU's stale-lap detector and Burnout 3's captured-pushbuffer menu replay (`src/nv2a/nv2a_pb_replay.c:1-5`). Network ordinals are stubs (`PhyGetLinkState` returns no link, `gap-analysis.md:80`). What exists that a rollback port would build on: all guest memory is one 64 MB mapping plus a per-thread register file in TLS, so the game-state snapshot is bounded and addressable; `RECOMP_GUEST_LOCK` + `--back-edge-yield` give one-CPU scheduling; `RECOMP_VBLANK=paced` + `RECOMP_FLIP_PACING` give a frame clock; `RECOMP_PAD_SCRIPT` is input injection; `RECOMP_FB_DUMP_FLIPS` records frames. What is missing: every time source is the host clock, so there is no fixed seed or virtual timebase (the Tekken 6 `T6_FIX_SEED`/`T6_VIRTUAL_TB` idea would be a kernel-bridge change); kernel objects, APU voices, executor state and real OS threads are not in the snapshot; and there is no frame-boundary hook. Nothing here moves us toward rollback that XboxXBERecomp's own runtime would not need to provide equally.

## 7. Comparison with XboxXBERecomp

| | XboxXBERecomp (per `docs/PRIOR-ART.md:20-28`) | xboxrecomp v0.16.0 |
|---|---|---|
| Proven playable ports | BLACK (V2), Splinter Cell: Double Agent, 007: From Russia With Love | None. Burnout 3 claim retired (`README.md:402`); Half-Life 2 title screen; Black boot scene |
| XDK handling | API level: D3D8, DirectSound, XAPI, XNet reimplemented; per-XDK-build signatures (`xbe_symbols`) | Hardware level: XDK lifted verbatim; NV2A pushbuffer executor, xemu MCPX APU, OHCI; HLE at `xboxkrnl` only; no XDK signature DB, ordinal remap by name (sections 1-2) |
| Graphics backend | Direct3D 12 | CPU rasteriser into guest RAM, presented via GDI or a D3D11 swap chain; optional back-end interface for pre-transformed triangles; D3D8-to-D3D11/OpenGL only for hand-shimmed titles |
| Platforms | Windows x64 | Windows x64 (MSVC, MinGW), Linux and macOS x86-64/arm64 (SDL2 + OpenGL, arm64 MMIO trap decoder, `README.md:32-33,167,911-923`) |
| Build requirements | Clang/LLD/Ninja/CMake, fetches Zydis etc.; player-side first-launch build | Python 3.10 + capstone; VS 2022 or Clang/GCC; CMake 3.20; millions of lines of generated C, `--split 250`, 365 MB `/O2` rebuilds (`README.md:1339,1853`); no player-side build story |

**Verdict.** xboxrecomp is not a credible main toolchain for MK today: no playable title, a CPU rasteriser as the default renderer, and a lifter whose correctness history is long and recent. It is a strong *reference*: the clearest public description of what XDK D3D8LTCG expects from the GPU, a working APU and OHCI model if any XDK code must run as-is, a parser/discovery/RTTI/naming toolbox that is XDK-version-agnostic, and a conformance methodology worth copying. Use it for pieces 1-4 and 8 of section 5 now, keep 5-7 in reserve for whatever XboxXBERecomp's API-level runtime cannot shim in MK (Dolby/DSP images, pushbuffer-level tricks), and expect to write the rollback layer ourselves either way.
